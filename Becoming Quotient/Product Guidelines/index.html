Product Design Guideline

A practical playbook for building consistent, usable BQ product screens — written for anyone shipping UI, not just designers. It leans on the BQ brand where that helps recognition, and leans on standard UX convention everywhere users' expectations matter more than brand expression.

The one rule that resolves every judgment call: brand shows up in color, type, and voice — usability rules (contrast, feedback, predictable patterns) are never negotiable. If a brand treatment would make something harder to read, slower to use, or less accessible, usability wins.

When brand leads vs. when convention leads

SurfaceBrand leadsConvention leads
Marketing pages, empty states, onboarding, hero moments Paper Beige background, P22 Mackinac headlines, ink-blue accents, real-people photography —
Dense product UI — dashboards, tables, forms, settings Ink-blue accent for interactive elements, BecomingSansSerif for all text White canvas (not beige), standard component patterns, no display serif in UI chrome
Status & system feedback — errors, success, warnings Colors are drawn from a BQ-consistent, muted palette Red = error, green = success, amber = warning — never remapped, color is never the only signal
Navigation, forms, tables, modals Accent color for active/selected state only Structure, spacing, and interaction follow this guide's component specs exactly

Every component below ships as a live example, not just a description — copy the pattern, don't reinterpret it.

DoUse Paper Beige for onboarding, empty states, and marketing surfaces where a brand mood matters.
Don'tUse Paper Beige as the background for dashboards or tables — off-white beige under long reading sessions reduces perceived contrast versus true white.
DoReserve Ink Blue for things users can act on: buttons, links, active nav, focus rings.
Don'tPaint large decorative blocks in Ink Blue — it reads as "clickable" and trains users to distrust the color.

Contrast minimums

Every color pairing above meets WCAG AA when used as specified: Ink on white/beige is 14.9:1, Ink Blue on white is 8.6:1, Error red on white is 6.1:1. If you introduce a new tint, check it against 4.5:1 for text and 3:1 for UI components before shipping — see Accessibility.

Foundations

Typography

Two typefaces, two jobs. P22 Mackinac carries brand voice at large sizes; it is not a UI font. BecomingSansSerif (the product/UI sans) does everything else — labels, body copy, tables, forms, buttons.

DoUse P22 Mackinac for page headlines and hero moments (32px and above), where brand recognition matters most.
Don'tSet body copy, table data, form labels, or buttons in P22 Mackinac — serif at small sizes and only one available weight hurts legibility and hierarchy in dense UI.

Rules of thumb

DoKeep body text between 14–16px. Never set readable paragraph text below 13px.
Don'tUse more than 3 type sizes on a single screen — pick from the scale above, don't invent one-off sizes.
DoLeft-align body text and UI labels; keep line length under ~75 characters for paragraphs.
Don'tCenter-align body copy or use italics — BQ's own type rule is no italics anywhere.

Foundations

Icons & imagery

Photography is where BQ's brand voice shows up most — real people, natural light, no studio gloss. Icons are functional and should stay quiet.

DoPick one icon style (outline, 24px grid, 1.5–2px stroke) and use it everywhere in product UI.
Don'tMix outline and filled icon sets, or pull icons from multiple libraries — inconsistent stroke weight is one of the fastest ways a product looks unpolished.
DoUse candid, real-people photography (per brand guide) for marketing pages, empty states, and onboarding illustration.
Don'tUse stock "corporate handshake" photography or studio-lit portraits — it breaks the brand's documented photographic style.

Components

Buttons

One primary action per screen. Every other action is secondary or tertiary.

Types

States

DoWrite button labels as verbs that state the outcome: "Save changes", "Create project", "Send invite".
Don'tUse vague labels like "Submit", "OK", or "Yes" — they force users to re-read the surrounding context to know what happens.
DoKeep buttons at minimum 40px tall (44px on touch) with at least 16px horizontal padding.
Don'tPut two primary (filled) buttons next to each other — it forces the user to guess which action actually matters.

Components

Forms & inputs

Labels always visible, errors always specific, focus states always obvious.

We'll send your confirmation here.
Password needs at least 8 characters — you have 5.
DoPut labels above the field, always visible — not only as placeholder text that disappears on input.
Don'tUse placeholder text as a substitute for a label. Once a user types, they lose the field's purpose entirely.
DoWrite error messages that state what went wrong and how to fix it: "Password needs at least 8 characters — you have 5."
Don'tShow generic errors like "Invalid input" — they leave the user guessing.
DoValidate on blur or submit, not on every keystroke — errors appearing mid-type feel punitive.
Don'tRemove the visible focus outline. Every input needs a visible focus state for keyboard users.

Components

Modals & overlays

Modals interrupt. Use them only when the user must decide or confirm something before continuing — never for content that could live on the page.

Delete this project?

This can't be undone. All files and history will be permanently removed.

DoGive every modal one primary action and one clear way to dismiss it (Cancel, Esc key, or backdrop click for non-destructive modals).
Don'tStack a modal on top of another modal. Close the first before opening the next.
DoTrap keyboard focus inside the modal while it's open, and return focus to the triggering element on close.
Don'tUse a modal to show information the user just needs to read — a panel or page section works better and doesn't block the rest of the UI.

Patterns

Responsive layout

Design mobile-first: get the single-column case right, then add columns as space allows. Don't design desktop first and shrink it later.

DoStack multi-column layouts into a single column below 600px; collapse sidebar nav into a bottom bar or hamburger menu.
Don'tShrink touch targets below 44×44px on mobile, even if the equivalent desktop control is smaller.
DoLet type and spacing scale fluidly between breakpoints rather than jumping abruptly at each one.
Don'tHide core functionality on mobile "to simplify" — move it into a menu instead of removing it.

Patterns

Empty, loading & error states

Every screen that can show data needs three more designs: what it looks like with nothing, while loading, and when something breaks.

Loading — use skeletons, not spinners, for content

Skeletons preserve layout and feel faster than a centered spinner because the user already sees where content will land. Reserve spinners for short (<1s) button-level waits.

Patterns

Onboarding

Teach inside the product, in context, rather than in front of it.

DoUse progressive disclosure — a short setup checklist, tooltips on first use, or a single welcome screen with a clear first action.
Don'tForce new users through a 6-step modal tour before they've touched the product. Most of it will be forgotten before it's relevant.
DoLet users skip or dismiss onboarding at any point and resume later from Settings or Help.
Don'tBlock core functionality behind an onboarding flow that can't be exited.

Accessibility essentials

Non-negotiable minimums — these aren't "nice to have," they determine whether part of your audience can use the product at all.

RuleMinimum
Text contrast4.5:1 for normal text, 3:1 for large text (18px+/14px bold+)
UI component contrast3:1 for icons, borders, and input outlines against their background
Touch targets44×44px minimum on touch devices, 40×40px minimum on desktop
Focus visibilityEvery interactive element shows a visible focus ring on keyboard nav
Keyboard accessEvery action reachable by mouse must also work via keyboard alone
Color independenceNever use color as the only signal — pair with icon, label, or pattern
Alt textEvery meaningful image has descriptive alt text; decorative images use empty alt
MotionRespect prefers-reduced-motion — offer a static alternative to animation
DoAssociate every form label with its input using <label for> so screen readers announce it correctly.
Don'tCommunicate an error with red border color alone — this example pairs red with an icon-equivalent dot and explicit text, see Feedback.

Standards

Content & microcopy

Product copy is measured and direct — plain language over cleverness, specific over generic, matching BQ's brand voice of restraint.

DoUse sentence case for all UI labels, buttons, and headings: "Create new project", not "Create New Project."
Don'tUse Title Case or ALL CAPS for buttons and labels (small uppercase eyebrows/tags are the one intentional exception).
DoWrite errors as: what happened + why (if useful) + what to do next.
Don'tUse exclamation points, or blame the user ("You entered an invalid value").
DoKeep confirmation dialogs to one direct sentence: "Delete this project? This can't be undone."
Don'tUse jargon, idioms, or internal team terms in user-facing copy — write for someone using the product for the first time.

Standards

Quick reference

The condensed version — for when you already know the guide and just need a fast check before shipping.

Always

  • One primary button per screen
  • Visible focus states on every control
  • Specific, actionable error messages
  • Labels above form fields, always visible
  • 4.5:1 text contrast minimum
  • 44px minimum touch targets
  • Sentence case for UI copy
  • Skeletons for content loading, spinners for quick actions

Never

  • Two primary (filled) buttons side by side
  • Placeholder text used as the only label
  • Color as the sole signal for status
  • Paper Beige background on dense/data UI
  • P22 Mackinac below 18–20px or in UI chrome
  • Stacked modals
  • Onboarding flows with no skip/exit
  • Mixed icon styles in the same product
